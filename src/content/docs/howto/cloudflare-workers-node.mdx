Cloudflare's free tier is the least annoying way to put a small Node service on
the internet: no sleeping containers, no cold starts worth measuring, no credit
card, and TLS plus a global CDN you don't configure. The catch is that Workers
run on `workerd`, not Node, so "deploy your Node project" means "run your code
on a runtime that emulates Node well enough" — which, as of 2025, includes
running an unmodified Express app.

## What free actually covers

| Limit | Free plan |
| --- | --- |
| Requests to your code | 100,000/day, resetting at 00:00 UTC |
| CPU time | 10 ms per request |
| Memory | 128 MB per isolate |
| Worker bundle | 3 MB compressed |
| Subrequests (outbound `fetch`) | 50 per request |
| Static asset requests | Free and unlimited |
| Static assets per version | 20,000 files, 25 MiB each |
| Workers per account | 100 |
| Cron triggers | 5 per account |

Two of those numbers matter more than the rest.

**10 ms of CPU is less scary than it sounds.** It's CPU time, not wall-clock
time — waiting on a database, an upstream API, or the client costs you nothing.
A JSON endpoint that queries a database and serializes the result uses well
under a millisecond. What blows the budget is CPU-bound work: image resizing,
bcrypt with a high cost factor, parsing a 5 MB document, rendering a large
React tree.

**Static assets are free and unlimited**, and only requests that actually invoke
your code count against the 100,000. A site that is mostly HTML, CSS, and images
with a few API routes burns almost none of the quota.

:::note
There is no overage billing on the free plan. Past the daily request limit,
Cloudflare starts returning errors until midnight UTC rather than charging you.
That's a feature for a hobby project and a problem for anything you care about —
$5/month moves you to 10 million requests and 30 seconds of CPU.
:::

## The runtime is not Node

Workers run in V8 isolates, so the mental model shifts in a few places:

- **No process that stays alive.** Module-level state survives between requests
  on a warm isolate, but you cannot rely on it. No in-memory session store, no
  `setInterval` background jobs — use [Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/)
  for scheduled work.
- **No native modules.** Anything shipping a `.node` binary (`sharp`, `bcrypt`,
  `better-sqlite3`) will not build. Swap to a pure-JS or WASM equivalent —
  `bcryptjs`, or the platform's own `crypto.subtle`.
- **No `child_process`.** There is nothing to spawn.
- **Node built-ins come from a compatibility layer.** `node:crypto`, `node:path`,
  `node:stream`, `node:buffer`, `node:http` and about two dozen others work.
  For a `compatibility_date` of `2026-08-04` or later they're on by default;
  before that, add the `nodejs_compat` flag. `node:http2`, `node:vm`, and
  `node:cluster` exist as stubs that import but don't run.

## Deploy from a GitHub repo, no CLI

Workers Builds watches a repository and deploys on push, which is the shortest
path if the code already lives on GitHub. It's the same product Pages used —
build, then deploy — pointed at a Worker.

<Steps>

1. Commit a `wrangler.jsonc` to the repository root. The dashboard path still
   needs one, and the `name` in it **must match** the Worker's name in
   Cloudflare or the build fails:

   ```jsonc title="wrangler.jsonc"
   {
   	"name": "notes-api",
   	"main": "src/index.js",
   	"compatibility_date": "2026-08-04",
   	"compatibility_flags": ["nodejs_compat"]
   }
   ```

2. In the dashboard, go to **Workers & Pages → Create**, then choose to import
   an existing Git repository. Authorize the **Cloudflare Workers & Pages**
   GitHub App when prompted, and scope it to **only select repositories** rather
   than the whole account.

3. Set the build settings:

   | Setting | Value |
   | --- | --- |
   | Build command | `npm run build` — or leave empty if there's no build step |
   | Deploy command | `npx wrangler deploy` (the default) |
   | Root directory | `/`, or the subdirectory in a monorepo |
   | Production branch | `main` |

4. Push a commit. The build log is under **Settings → Builds** on the Worker.

</Steps>

After that, a push to `main` deploys to production. A push to any other branch
runs `npx wrangler versions upload` instead — it builds and gives you a preview
URL without touching what's live, which makes a pull request a testable
deployment.

Build settings you'll want eventually:

- **Build watch paths** — in a monorepo, stop every commit from rebuilding
  every Worker.
- **Build-time environment variables** — separate from runtime `vars`, and not
  readable at runtime. `WORKERS_CI_BRANCH` and `WORKERS_CI_COMMIT_SHA` are
  injected for you.
- **Deploy command `npx wrangler versions upload`** on production too, if you'd
  rather promote releases by hand than have every merge go live.

Free plan builds: **3,000 build minutes/month**, one build at a time, and a
20-minute ceiling per build.

:::tip
An existing Worker you first deployed from your laptop can be connected to a
repo later — **Settings → Builds → Connect**. It doesn't have to be decided up
front.
:::

## Set up wrangler

Worth having even if the dashboard does your deploys: `wrangler` is what runs
the project locally, creates databases, sets secrets, and tails production logs.
Install it per-project rather than globally so the version is pinned in
`package.json` — Workers Builds then uses that same pinned version:

```bash
npm install -D wrangler
```

Authenticate through the browser:

```bash
npx wrangler login
```

On a headless box, create an API token in the dashboard under **My Profile →
API Tokens** using the "Edit Cloudflare Workers" template, and export it
instead:

```bash
export CLOUDFLARE_API_TOKEN=your-token-here
```

## Or deploy from the command line

<Steps>

1. Scaffold a project. C3 writes the config, a starter handler, and a
   `package.json`:

   ```bash
   npm create cloudflare@latest -- notes-api
   ```

2. Run it locally. This is the real runtime, not an emulator, on
   `localhost:8787`:

   ```bash
   npx wrangler dev
   ```

3. Ship it:

   ```bash
   npx wrangler deploy
   ```

</Steps>

The deploy prints a URL like `https://notes-api.bferg.workers.dev`. That
subdomain is free and permanent, and it's enough for a project nobody needs to
remember the address of.

## Bring an existing Express app

`httpServerHandler` bridges a Node HTTP server to the Workers request model, so
an Express app deploys with a two-line change to the entry file. It needs
`nodejs_compat` and a `compatibility_date` of `2025-09-01` or later.

<Tabs syncKey="framework">
	<TabItem label="Express">
		```js title="src/index.js"
		import { httpServerHandler } from "cloudflare:node";
		import express from "express";

		const app = express();
		app.use(express.json());

		app.get("/health", (req, res) => {
			res.json({ ok: true });
		});

		app.listen(3000);
		export default httpServerHandler({ port: 3000 });
		```
	</TabItem>
	<TabItem label="Hono">
		```js title="src/index.js"
		import { Hono } from "hono";

		const app = new Hono();

		app.get("/health", (c) => c.json({ ok: true }));

		export default app;
		```

		Hono is Express-shaped but built for this runtime — no compatibility
		layer, a much smaller bundle, and typed access to bindings. Worth the
		hour it takes to port a small router.
	</TabItem>
	<TabItem label="Plain handler">
		```js title="src/index.js"
		export default {
			async fetch(request, env, ctx) {
				const url = new URL(request.url);
				if (url.pathname === "/health") {
					return Response.json({ ok: true });
				}
				return new Response("Not found", { status: 404 });
			},
		};
		```
	</TabItem>
</Tabs>

The matching config:

```jsonc title="wrangler.jsonc"
{
	"name": "notes-api",
	"main": "src/index.js",
	"compatibility_date": "2026-08-04",
	"compatibility_flags": ["nodejs_compat"],
	"workers_dev": true,
	"observability": { "enabled": true }
}
```

:::tip
`wrangler.toml` works identically if you prefer it — every key maps one to one.
JSONC is what `npm create cloudflare` writes now, and it tolerates comments.
:::

What still trips up a ported Express app: middleware that reads from disk at
request time, anything CPU-heavy in a `use()` hook that now runs on every
request inside a 10 ms budget, and `process.env` reads — configuration arrives
as a binding, covered below.

## Static site plus API in one Worker

Point `assets` at your build output. Cloudflare serves matching paths straight
from the CDN and only invokes your code when nothing matches — or, with
`run_worker_first`, for the paths you name.

```jsonc title="wrangler.jsonc"
{
	"name": "notes",
	"main": "src/index.js",
	"compatibility_date": "2026-08-04",
	"assets": {
		"directory": "./dist",
		"binding": "ASSETS",
		"not_found_handling": "single-page-application",
		"run_worker_first": ["/api/*"]
	}
}
```

That single Worker is now a static frontend and a backend, and the frontend's
traffic doesn't count against your request quota. Astro, SvelteKit, Nuxt, and
Remix all have official Cloudflare adapters that generate this layout;
Next.js goes through [`@opennextjs/cloudflare`](https://opennext.js.org/cloudflare).

## Sub-sites on your own domain

Custom domains are free on the free plan. The one requirement is that the
domain's nameservers point at Cloudflare, which you set up once when you add
the zone to your account.

Give each service its own hostname by declaring routes in the config:

```jsonc title="wrangler.jsonc"
{
	"routes": [
		{ "pattern": "notes.bferg.dev", "custom_domain": true },
		{ "pattern": "api.bferg.dev", "custom_domain": true }
	]
}
```

On deploy, Cloudflare creates the DNS records and issues the certificates
itself. Nothing to renew, nothing to configure.

Two ways to slice a domain across projects:

- **One Worker per subdomain.** `notes.bferg.dev` and `api.bferg.dev` are
  separate Workers with separate deploys, quotas shared at the account level.
  This is the right default — a bad deploy of one can't take down the other.
- **One Worker, several hostnames.** List multiple patterns on one Worker and
  branch on `new URL(request.url).hostname`. Fewer deploys, one blast radius.

For **path-based** routing under an existing site, drop `custom_domain` and use
a pattern with a path:

```jsonc title="wrangler.jsonc"
{
	"routes": [{ "pattern": "bferg.dev/api/*", "zone_name": "bferg.dev" }]
}
```

:::caution
A path route only fires if a **proxied** DNS record already exists for that
hostname — custom domains create one for you, plain routes don't. If the
hostname has no origin, the conventional placeholder is a proxied `AAAA` record
pointing at `100::`, the IPv6 discard prefix.
:::

Custom domains match exactly and don't accept wildcards, so
`*.bferg.dev` needs a route pattern rather than a custom domain.

### Staging on the same domain

Environments give you a second deploy of the same code with its own hostname
and its own bindings:

```jsonc title="wrangler.jsonc"
{
	"env": {
		"staging": {
			"routes": [{ "pattern": "notes-staging.bferg.dev", "custom_domain": true }]
		}
	}
}
```

```bash
npx wrangler deploy --env staging
```

:::tip[Hosting on your LAN instead?]
Public hostnames get certificates automatically here. For services that only
exist inside your network, see [Run a Local CA](./local-ca.mdx).
:::

## Configuration and secrets

Non-secret values go in the config file and arrive on `env`:

```jsonc title="wrangler.jsonc"
{
	"vars": { "LOG_LEVEL": "info" }
}
```

Secrets never go in the config file — they're encrypted at rest and write-only
once set:

```bash
npx wrangler secret put SESSION_KEY
```

For local development, put the same names in a git-ignored file:

```ini title=".dev.vars"
SESSION_KEY=dev-only-not-the-real-one
```

In a Worker handler these are `env.SESSION_KEY`. In ported Node code, import
the same object directly:

```js
import { env } from "cloudflare:workers";
```

## Free database options

### D1 — start here

D1 is SQLite, managed, with a binding that's already in your Worker. No
connection string, no pool, no cold-start handshake.

| D1 free tier | |
| --- | --- |
| Rows read | 5 million/day |
| Rows written | 100,000/day |
| Storage | 5 GB total per account |
| Databases | 10, max 500 MB each |
| Queries per invocation | 50 |
| Point-in-time recovery | 7 days |

<Steps>

1. Create the database. The command prints the binding block to paste into
   your config:

   ```bash
   npx wrangler d1 create notes-db
   ```

2. Add it to the config with the ID from that output:

   ```jsonc title="wrangler.jsonc"
   {
   	"d1_databases": [
   		{
   			"binding": "DB",
   			"database_name": "notes-db",
   			"database_id": "b1f2c3d4-5e6f-4a7b-8c9d-0e1f2a3b4c5d"
   		}
   	]
   }
   ```

3. Write a schema:

   ```sql title="schema.sql"
   CREATE TABLE IF NOT EXISTS notes (
   	id INTEGER PRIMARY KEY,
   	body TEXT NOT NULL,
   	created_at TEXT NOT NULL DEFAULT (datetime('now'))
   );
   ```

4. Apply it locally, then to production:

   ```bash
   npx wrangler d1 execute notes-db --local --file=./schema.sql
   ```

   ```bash
   npx wrangler d1 execute notes-db --remote --file=./schema.sql
   ```

</Steps>

Querying uses prepared statements — always bind parameters, never interpolate:

```js title="src/index.js"
export default {
	async fetch(request, env) {
		const { results } = await env.DB
			.prepare("SELECT id, body FROM notes WHERE created_at > ? LIMIT 20")
			.bind("2026-01-01")
			.all();
		return Response.json(results);
	},
};
```

`wrangler dev` runs against a local SQLite file by default, so you can break
things freely. Add `--remote` to run against the real database.

### The rest of the Cloudflare shelf

| Service | Shape | Free tier |
| --- | --- | --- |
| **KV** | Eventually-consistent key/value, read-optimized | 100,000 reads/day, 1,000 writes/day, 1 GB |
| **R2** | S3-compatible object storage | 10 GB-month, 1M Class A + 10M Class B ops/month, **no egress fees** |
| **Durable Objects** | A single addressable object with its own storage — coordination, websockets, rate limiting | Included on the free plan (SQLite-backed classes) |
| **Hyperdrive** | Pooling and caching in front of a Postgres/MySQL server you already run | 100,000 queries/day |

KV's 1,000 writes/day is the sharp edge — it's built for config, feature flags,
and cached responses, not for anything a user writes to.

### Postgres from a Worker

Workers can't open an arbitrary TCP connection the way Node can, and a
per-request Postgres handshake would be slow even if they could. Three ways
around it, in order of how little work they are:

1. **An HTTP driver.** Neon's `@neondatabase/serverless` and `supabase-js`
   speak HTTP and work in a Worker with no extra plumbing.
2. **Hyperdrive.** Point it at any Postgres or MySQL URL, bind it, and use a
   normal driver like `postgres`; Cloudflare keeps the pool warm on its side.
3. **Direct TCP** via `connect()` from `cloudflare:sockets`, which the
   `postgres` driver supports. Works, but you own the connection lifecycle.

Free tiers worth knowing, all verified in mid-2026 — these move, so check the
pricing page before you commit:

| Provider | Free tier | Note |
| --- | --- | --- |
| [Neon](https://neon.com/pricing) | Postgres, 0.5 GB per project, up to 10 projects | Scales to zero; HTTP driver; branching per git branch |
| [Supabase](https://supabase.com/pricing) | Postgres, 500 MB, 5 GB egress, 2 projects | Auth and storage included; **pauses after 7 days idle** |
| [Turso](https://turso.tech/pricing) | SQLite/libSQL, 5 GB, 500M row reads/month | Closest thing to D1 if you want it portable |
| [MongoDB Atlas](https://www.mongodb.com/pricing) | M0 cluster, 512 MB | Use the Data API, not the Node driver |
| [Upstash](https://upstash.com/pricing) | Redis and queues, per-request pricing with a free allowance | HTTP-native, designed for this runtime |

The auto-pause behavior is what usually decides it. A Supabase project that
sleeps after a week of no traffic is fine for a side project and miserable for
something you check monthly. D1 and Neon don't pause.

## Deploy from GitHub Actions instead

Workers Builds covers most cases, but a Worker is one job in a longer pipeline —
tests first, or a deploy that has to wait on something else — Actions gives you
that control. Add `CLOUDFLARE_API_TOKEN` as a repository secret, then:

```yaml title=".github/workflows/deploy.yml"
name: Deploy
on:
  push:
    branches: [main]
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - uses: cloudflare/wrangler-action@v3
        with:
          apiToken: ${{ secrets.CLOUDFLARE_API_TOKEN }}
```

## Once it's live

Stream logs from production, filtered to what you care about:

```bash
npx wrangler tail --status error
```

List what's deployed, and roll back when a deploy was a mistake:

```bash
npx wrangler deployments list
```

```bash
npx wrangler rollback
```

With `"observability": { "enabled": true }` in the config, logs are also
queryable in the dashboard for a week without any extra service.

## Gotchas worth knowing before you commit

- **The 3 MB compressed bundle is a real ceiling.** A dependency tree built for
  Node hits it faster than you'd expect. `npx wrangler deploy --dry-run
  --outdir=dist` shows the size without shipping anything.
- **`Date.now()` doesn't advance during synchronous execution.** It's frozen
  until the next I/O to prevent timing attacks. Benchmarking inside a Worker
  measures nothing.
- **The daily reset is UTC**, not your timezone.
- **Free-plan limits are per account, not per Worker.** Ten side projects share
  one bucket of 100,000 requests.
- **Local dev is not fully local.** `wrangler dev` runs the real runtime on your
  machine, but bindings to remote-only services still reach out. `--local` and
  `--remote` decide which.
